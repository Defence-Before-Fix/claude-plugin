# Shell

An instance of [the toolchain contract](CONTRACT.md). The Semgrep and ast-grep grades are from
`register.json`; ShellCheck is not in the register, so it is ungraded unless the register has
gained an entry since.

## Detection

Tracked `*.sh`, `*.bash`, `*.bats` or `*.zsh` files, and files with no extension whose first line
is a shell shebang (`#!/bin/sh`, `#!/bin/bash`, `#!/usr/bin/env bash` and the like), which are
common in `bin/` and `scripts/`. Shell turns up in projects of every language, so look for it
even when another language is the main one:

```bash
git ls-files -z | xargs -0 awk 'FNR == 1 && /^#!.*[\/ ](ba|da|k|z)?sh([[:space:]]|$)/ { print FILENAME } { nextfile }'
```

That reads only the first line of each file, so a shebang quoted inside a document or a test
does not count. It finds scripts by shebang only; add `git ls-files '*.sh' '*.bash'` for sourced
files, which often have none.

## Entry point

Rarely a dedicated one. Look for `shellcheck` in the `Makefile`, `.pre-commit-config.yaml` or CI,
and for a `bats` test directory. Where shell is a minor language in a larger project, its checks
are part of that project's entry point.

## Rule host

| Host                         | Grade    | Use it for                                                               |
| ---------------------------- | -------- | ------------------------------------------------------------------------ |
| Semgrep, `bash` grammar      | Amber    | Command and argument patterns: an unquoted expansion, a missing flag     |
| ast-grep, `bash` grammar     | Green    | The same, where the project already uses ast-grep                        |
| A line-level check script    | Ungraded | Classes Semgrep's bash grammar cannot parse, such as some here-documents |
| An existing ShellCheck check | Ungraded | A class one of its bundled checks already detects                        |
| ShellCheck, bespoke          | Ungraded | Nothing bespoke: a fixed catalogue. Keep running it as a check           |

Semgrep's bash support covers POSIX `sh` and bash; it does not parse zsh or fish. A check script
for shell is usually `awk` or `grep -n -E` over the file list, and has to meet the contract's
[check scripts](CONTRACT.md#check-scripts) section like any other.

## Harness and proof

- Semgrep:
  `semgrep scan --no-rewrite-rule-ids --config <rule-file> --error --scan-unknown-extensions <file>`,
  and `semgrep scan --test <rules-dir>` for the fixtures; give fixtures a `.sh` or `.bash`
  extension so nothing depends on shebang detection. The `# ok:` half of the fixture pair
  matters here: in a pattern, `$X` is a Semgrep metavariable that matches any argument, quoted,
  unquoted or literal, not a shell variable, so a rule about shell expansions is easily drawn
  wider than the hazard, and only the silent fixture shows it.
- Check script: run it on the fixture file and check the exit code and the printed identifier.
- Tests for shell behaviour, including the original defect's reproducing test, go in bats-core
  (`bats <dir>`) or whatever harness the project already uses.

## Identifier and page

Semgrep and a check script print what their message carries, so the message starts with the
identifier and names the page. ShellCheck prints an `SC` code with every finding in its default
and `gcc` formats (JSON carries the number without the prefix, and the `diff` and `quiet`
formats print none); the codes' documentation is the ShellCheck wiki, online only.

## Sweep

Build the file list explicitly from the detection commands above and pass it to the tool, with
`--scan-unknown-extensions` for Semgrep. A Semgrep directory walk picks up an extensionless
script only when it is executable and has a shebang Semgrep recognises, and skips `tests/` by
default, so a walk can miss scripts without saying so. Exclude vendored scripts,
`node_modules/`, and scripts generated by build tools.

## Listing and project record

Semgrep rules are listed by the files in the rules directory; ShellCheck has no rule listing
beyond its wiki. `.shellcheckrc` at the project root, with `disable=SCxxxx` lines, is the
project-level place for an exception, and a comment above each line is its justification;
nothing rejects a missing one.

## Suppression routes

| Route                                      | Tool       | What closes it                 |
| ------------------------------------------ | ---------- | ------------------------------ |
| `# shellcheck disable=SCxxxx` above a line | ShellCheck | A rule of the project's own    |
| The same directive at the top of the file  | ShellCheck | A rule of the project's own    |
| `# nosemgrep`                              | Semgrep    | `semgrep scan --disable-nosem` |

A rule of the project's own for these directives is a Semgrep `pattern-regex` rule or a
`grep -n -E '#[[:space:]]*shellcheck[[:space:]]+disable'` check. Whether to close a route on a
tool the project already runs is the owner's decision, as the contract's
[suppression routes](CONTRACT.md#listing-project-record-and-suppression-routes) paragraph says.

## Runner

bats-core, shunit2, or the project's own test scripts. Where the scripts are exercised only
through another language's tests, that suite is the runner.

## CI hook

`.github/workflows/`, `.gitlab-ci.yml`, `Makefile` and `.pre-commit-config.yaml`. Record
whether CI's ShellCheck and Semgrep invocations see extensionless scripts too.

## Known gaps

- ShellCheck cannot host a bespoke rule, is not graded in the register, and resolves its codes
  online only.
- No shell detector offers a listing of project rules.
